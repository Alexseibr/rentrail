## 1. Архитектура системы

```
┌─────────────────────────────────────────────────────────┐
│                   Replit Proxy (порт 80)                │
│              маршрутизация по path-prefix               │
└──────────┬──────────────────────┬───────────────────────┘
           │                      │
    /api/* → API Server    /* → Platform Admin
           │
    ┌──────▼──────────────────┐
    │  API Server (Express 5) │  порт из $PORT
    │  @workspace/api-server  │
    ├─────────────────────────┤
    │  PostgreSQL + Drizzle   │
    │  JWT (access 15м +      │
    │  refresh 30д)           │
    └─────────────────────────┘
           │
    ┌──────▼──────────────────┐
    │  Staff App (Expo)       │  Expo Go / Tunnel
    │  iOS + Android + Web    │
    │  Режим: Staff / Client  │
    └─────────────────────────┘
```

**Мультитенантность:** каждый запрос к API требует заголовка `x-company-id` для изоляции данных по компаниям.

## 2. Аутентификация и авторизация

### 2.1 Вход по номеру телефона

```http
POST /api/auth/phone/login
Content-Type: application/json

{
  "phone": "+79991000001",
  "password": "demo1234"
}
```

**Ответ:**

```json
{
  "data": {
    "accessToken": "eyJ...",
    "refreshToken": "eyJ...",
    "user": {
      "id": "uuid",
      "firstName": "Maria",
      "lastName": "Johnson",
      "phone": "+79991000001"
    }
  }
}
```

Токены: access — 15 минут, refresh — 30 дней.

### 2.2 Информация о текущем пользователе

```http
GET /api/auth/me
Authorization: Bearer <accessToken>
```

### 2.3 Обновление токена

```http
POST /api/auth/refresh
Content-Type: application/json

{ "refreshToken": "eyJ..." }
```

### 2.4 Выход

```http
POST /api/auth/logout
Authorization: Bearer <accessToken>
```

### 2.5 Заголовки для запросов к API

Все защищённые эндпоинты требуют:

| Заголовок       | Значение               |
| --------------- | ---------------------- |
| `Authorization` | `Bearer <accessToken>` |
| `x-company-id`  | UUID компании          |

## 5. Сервисный модуль

### 5.1 Наряды на работу (Work Orders)

Нарядная система для учёта всех сервисных работ с транспортом.

#### Типы нарядов

| Тип                     | Описание                            |
| ----------------------- | ----------------------------------- |
| `field_repair`          | Полевой ремонт (выезд к транспорту) |
| `workshop_repair`       | Мастерская                          |
| `scheduled_maintenance` | Плановое ТО                         |
| `inspection`            | Осмотр                              |
| `recovery`              | Эвакуация                           |
| `cleaning`              | Мойка/чистка                        |

#### Приоритеты нарядов

| Приоритет | Описание               |
| --------- | ---------------------- |
| `low`     | Низкий                 |
| `medium`  | Средний (по умолчанию) |
| `high`    | Высокий                |
| `urgent`  | Срочный                |

#### Жизненный цикл наряда

```
draft → assigned → en_route → in_progress → waiting_parts → completed
                                                            ↘ canceled
```

#### API нарядов

```http
GET  /api/work-orders                    — список нарядов
POST /api/work-orders                    — создать наряд    [asset:update]
PATCH /api/work-orders/:id              — обновить наряд   [asset:update]
POST  /api/work-orders/:id/status       — изменить статус  [asset:update]
GET  /api/work-orders/:id/parts         — запчасти наряда
POST /api/work-orders/:id/parts         — добавить запчасть к наряду
DELETE /api/work-orders/:id/parts/:partId — убрать запчасть из наряда
```

**Создание наряда:**

```json
{
  "title": "Замена цепи KMC X11",
  "orderType": "workshop_repair",
  "priority": "high",
  "assetId": "uuid-актива",
  "description": "Износ цепи превышает 0.75%"
}
```

**Переход по статусам:**

```json
{ "status": "in_progress" }

{ "status": "completed", "actualCost": "950.00", "resolution": "Цепь заменена" }
```

**Получение списка механиков:**

```http
GET /api/mechanics
```

### 5.2 Журнал обслуживания (Maintenance Logs)

Фиксирует каждую выполненную работу по конкретному транспортному средству. Служит историей ТО.

#### Типы записей

| Тип                   | Описание              |
| --------------------- | --------------------- |
| `oil_change`          | Замена масла          |
| `tire_replacement`    | Замена шин            |
| `brake_service`       | Обслуживание тормозов |
| `battery_replacement` | Замена аккумулятора   |
| `chain_service`       | Обслуживание цепи     |
| `electrical_repair`   | Электрический ремонт  |
| `frame_repair`        | Ремонт рамы           |
| `general_service`     | Общее обслуживание    |
| `inspection`          | Осмотр                |
| `cleaning`            | Чистка                |
| `other`               | Прочее                |

#### API журнала

```http
GET  /api/maintenance-logs              — список записей (фильтр: ?assetId=)
POST /api/maintenance-logs             — создать запись  [asset:update]
```

**Создание записи:**

```json
{
  "assetId": "uuid-актива",
  "logType": "brake_service",
  "notes": "Заменены колодки Shimano BR-M420, регулировка хода ручки",
  "cost": "2500.00",
  "odometerKm": 3240,
  "performedAt": "2026-05-01T10:00:00Z"
}
```

Поле `performedAt` — опционально (по умолчанию — текущее время).

### 5.3 Расписание обслуживания (Maintenance Schedules)

Планировщик регулярного ТО по интервалу времени и/или пробегу.

#### Типы расписаний

| Тип                | Описание          |
| ------------------ | ----------------- |
| `inspection`       | Регулярный осмотр |
| `oil_change`       | Замена масла      |
| `tire_replacement` | Замена шин        |
| `brake_service`    | Тормоза           |
| `battery_check`    | Проверка батареи  |
| `chain_service`    | Цепь              |
| `general_service`  | Общее ТО          |
| `custom`           | Пользовательское  |

#### API расписаний

```http
GET    /api/maintenance-schedules          — список расписаний (?assetId=)
GET    /api/maintenance-schedules/overdue  — просроченные расписания
POST   /api/maintenance-schedules          — создать расписание  [asset:update]
PATCH  /api/maintenance-schedules/:id      — обновить расписание [asset:update]
DELETE /api/maintenance-schedules/:id      — удалить расписание  [asset:update]
```

**Создание расписания:**

```json
{
  "assetId": "uuid-актива",
  "scheduleType": "inspection",
  "name": "Плановое ТО каждые 90 дней",
  "intervalDays": 90,
  "intervalKm": 2000
}
```

Система автоматически обновляет `nextDueAt` и `nextDueKm` после каждой записи в журнале обслуживания соответствующего типа.

## 7. Staff App — мобильное приложение

Expo-приложение для iOS, Android и Web. Поддерживает два режима работы.

### 7.1 Режимы работы

**Staff Mode** — для сотрудников компании (авторизуются по телефону/паролю):

- Просмотр и управление флотом
- Работа с арендами
- Сервисный модуль (наряды, журнал ТО, склад)
- Push-уведомления

**Client Mode** — для клиентов-арендаторов:

- Просмотр доступных транспортных средств
- Управление своими арендами
- История поездок

### 7.2 Навигация Staff Mode

```
Нижнее меню:
├── Активы (assets)
│   ├── Список с поиском по коду/марке/модели
│   ├── Фильтры по статусу (chips)
│   └── Карточка: тип, статус, батарея, локация
├── Аренды (rentals)
│   ├── Список с поиском
│   ├── Фильтры по статусу и типу
│   └── Карточка с клиентом и суммой
├── Операции (operations)
│   ├── Быстрые действия (изменение статусов, уведомления)
│   └── Сервисный модуль:
│       ├── Наряды на работу (Work Orders)
│       ├── Журнал ТО (Maintenance Logs)
│       ├── Расписание ТО (Schedules)
│       └── Склад запчастей (Spare Parts)
└── Профиль (profile)
```

### 7.3 Экраны сервисного модуля

#### Наряды на работу (`/service/work-orders`)

- Список нарядов с фильтрами по статусу
- Карточка: тип, приоритет, статус, дата создания
- Статусы с цветовыми индикаторами (draft/in_progress/completed/canceled)

#### Журнал ТО (`/service/maintenance-logs`)

- История обслуживания по активам
- Создание новых записей
- Фильтр по типу работ

#### Расписание ТО (`/service/maintenance-schedules`)

- Список плановых ТО с индикатором «Просрочено»
- Создание по интервалу дней / км
- Автообновление после выполнения работ

#### Склад запчастей (`/service/spare-parts`)

- Список позиций с текущим остатком
- Кнопки «+ Поступление» / «− Выдача»
- История движения каждой позиции

### 7.4 Интернационализация (i18n)

Поддерживаются: **Русский (ru)** и **English (en)**.

Переведены:

- Статусы активов (available → «Доступен», rented → «В аренде» и т.д.)
- Типы активов (bike → «Велосипед», ebike → «Э-велосипед» и т.д.)
- Статусы аренды (все 8 статусов)
- Типы аренды (hourly → «Почасовая» и т.д.)
- Все экраны и компоненты навигации

## 9. Ролевая модель доступа (RBAC)

### 9.1 Системные роли

| Роль                | Код          | Описание                        |
| ------------------- | ------------ | ------------------------------- |
| Владелец            | `owner`      | Полный доступ ко всему          |
| Администратор       | `admin`      | Всё кроме управления компанией  |
| Менеджер            | `manager`    | Операции без удаления           |
| Оператор            | `operator`   | Работа с клиентами и арендами   |
| Механик             | `mechanic`   | Только сервис и статусы активов |
| Бухгалтер           | `accountant` | Финансовые операции             |
| Наблюдатель         | `viewer`     | Только чтение                   |
| Супер-администратор | `superAdmin` | Системный уровень               |

### 9.2 Матрица разрешений сервисного модуля

| Действие            | owner | admin | manager | mechanic | operator | viewer |
| ------------------- | ----- | ----- | ------- | -------- | -------- | ------ |
| Читать наряды       | ✅    | ✅    | ✅      | ✅       | —        | ✅     |
| Создавать наряды    | ✅    | ✅    | ✅      | —        | —        | —      |
| Обновлять наряды    | ✅    | ✅    | ✅      | ✅       | —        | —      |
| Читать журнал ТО    | ✅    | ✅    | ✅      | ✅       | —        | ✅     |
| Создавать записи ТО | ✅    | ✅    | ✅      | ✅       | —        | —      |
| Склад — чтение      | ✅    | ✅    | ✅      | ✅       | —        | ✅     |
| Склад — транзакции  | ✅    | ✅    | ✅      | —        | —        | —      |

> Разрешение `asset:update` даёт доступ к созданию/обновлению нарядов, журнала, расписаний, транзакций склада.  
> Разрешение `asset:read` даёт доступ к просмотру всех сервисных данных.

### 9.3 Проверка разрешений

Каждый защищённый эндпоинт проверяет:

1. Наличие валидного JWT (`authenticate`)
2. Членство пользователя в компании (`requireCompanyAccess`)
3. Наличие нужного разрешения (`requirePermission`)

При нарушении: `403 FORBIDDEN` с телом `{"error": {"code": "FORBIDDEN", "message": "Missing permission: ..."}}`

```json
{ "data": { ... } }
```

  "error": {

## Примеры полных сценариев

### Сценарий 1: Механик выполняет ТО велосипеда

```bash
# 1. Войти как механик
TOKEN=$(curl -s -X POST /api/auth/phone/login \
  -H "Content-Type: application/json" \
  -d '{"phone":"+79991000005","password":"demo1234"}' | jq -r '.data.accessToken')

# 2. Получить список активов
curl /api/assets -H "Authorization: Bearer $TOKEN" -H "x-company-id: $COMPANY"

# 3. Перевести актив в статус maintenance
curl -X PATCH /api/assets/$ASSET_ID/status \
  -d '{"status":"maintenance","reason":"Плановое ТО"}'

# 4. Создать запись в журнале ТО
curl -X POST /api/maintenance-logs \
  -d '{"assetId":"$ASSET_ID","logType":"brake_service","cost":"2500.00"}'

# 5. Вернуть актив в available
curl -X PATCH /api/assets/$ASSET_ID/status \
  -d '{"status":"available","reason":"ТО завершено"}'
```

### Сценарий 2: Полный цикл наряда на работу

```bash
# 1. Создать наряд
WO=$(curl -X POST /api/work-orders \
  -d '{"title":"Замена цепи","orderType":"workshop_repair","priority":"high"}')
WO_ID=$(echo $WO | jq -r '.data.id')

# 2. Взять в работу
curl -X POST /api/work-orders/$WO_ID/status -d '{"status":"in_progress"}'

# 3. Выписать запчасть со склада
curl -X POST /api/spare-parts/transactions \
  -d '{"partId":"$PART_ID","transactionType":"out","qty":1}'

# 4. Завершить наряд
curl -X POST /api/work-orders/$WO_ID/status \
  -d '{"status":"completed","actualCost":"950.00","resolution":"Цепь заменена"}'
```

### Сценарий 3: Управление складом запчастей

```bash
# Создать позицию
PART=$(curl -X POST /api/spare-parts \
  -d '{"name":"Колодки Shimano","sku":"SH-BR-001","category":"brakes","unit":"шт"}')
PART_ID=$(echo $PART | jq -r '.data.id')

# Поступление (+20 шт)
curl -X POST /api/spare-parts/transactions \
  -d '{"partId":"$PART_ID","transactionType":"in","qty":20}'

# Выдача (-3 шт)
curl -X POST /api/spare-parts/transactions \
  -d '{"partId":"$PART_ID","transactionType":"out","qty":3}'

# Проверить остаток → 17 шт
curl /api/spare-parts/$PART_ID | jq '.data.qtyInStock'
```

## 12. Что улучшить, чтобы клиенту было удобно пользоваться

Ниже — приоритетный список улучшений клиентского опыта (Client mode в Staff App + клиентские API).

### P0 (сразу в ближайший спринт)

1. **Онбординг в 3 шага после логина**
   - Шаг 1: как начать аренду;
   - Шаг 2: как завершить аренду и где смотреть стоимость;
   - Шаг 3: куда писать при проблемах.
   - Метрика успеха: снижение брошенных сессий в первые 10 минут.

2. **Прозрачная цена до старта аренды**
   - На экране старта показывать: тариф, депозит, возможные штрафы, итог «от/до».
   - Подтверждение чекбоксом перед стартом.
   - Метрика: меньше обращений «непонятно за что списали».

3. **Крупная кнопка “SOS / Проблема с поездкой” в активной аренде**
   - Быстрые сценарии: «не открывается замок», «авария», «не могу завершить аренду».
   - Автоподстановка `rentalId`, `assetId`, координат в заявку.
   - Метрика: сокращение времени до первого ответа поддержки.

4. **Упрощённый флоу завершения аренды**
   - Явная проверка зоны парковки (geofence) до нажатия “Завершить”.
   - Чеклист: фото парковки, закрыт замок, финальная сумма.
   - Метрика: снижение доли неуспешных завершений с первой попытки.

### P1 (после стабилизации базового флоу)

5. **Персональные подсказки по локации и времени**
   - Пуши: «рядом свободные велосипеды», «через 10 мин тариф сменится».
   - Тихий режим уведомлений ночью.

6. **Локализация и тон сообщений для клиента**
   - Единый понятный словарь ошибок без тех. терминов.
   - RU/EN тексты для ключевых сценариев (логин, старт, оплата, завершение).

7. **Экран “История поездок и чеков”**
   - По каждой аренде: маршрут, длительность, стоимость, чек/квитанция.
   - Кнопка «Оспорить списание» прямо в деталях поездки.

### P2 (рост конверсии и retention)

8. **Быстрый повтор аренды и избранные точки**
   - «Повторить прошлый маршрут», «дом/работа» как избранные места.

9. **Микро-NPS после 2–3 поездок**
   - Короткий опрос (1 вопрос + причина) и сегментация по проблемам.

10. **Реферальная механика и промокоды**
    - Промокод за первую успешную поездку друга.

### Дополнительно: что ещё улучшить именно по UX/UI

11. **Единая дизайн-система для клиентского режима**
    - Зафиксировать токены: цвета, отступы, типографика, радиусы, состояния кнопок.
    - Ввести UI-kit для экранов: карточка актива, тарифный блок, статус аренды, системные алерты.
    - Цель: снизить визуальную “разрозненность” и ускорить разработку новых экранов.

12. **Контраст и доступность (A11y) как дефолт**
    - Контраст текста и кнопок не ниже WCAG AA.
    - Интерактивные элементы с высотой не менее 44px.
    - Все ключевые действия доступны одной рукой (зона большого пальца).
    - Цель: меньше ошибок на улице/на солнце, выше completion rate.

13. **Сильные пустые состояния и состояния загрузки**
    - Для каждого экрана: Empty / Loading / Error / Offline.
    - Пустые состояния с CTA: “Найти ближайший транспорт”, “Повторить попытку”.
    - Скелетоны вместо “дёрганья” интерфейса.

14. **Сократить количество шагов в критических сценариях**
    - Старт аренды: максимум 2 касания после выбора актива.
    - Завершение аренды: максимум 3 касания + 1 фото.
    - Убрать необязательные поля в моменте поездки, переносить в пост-флоу.

15. **Переосмыслить карту как основной экран клиента**
    - Яркий приоритет ближайших доступных активов.
    - Фильтры “только с батареей > X%”, “только у станции”, “без депозита”.
    - Плашка ETA пешком до выбранного транспорта.

16. **Платёжные шаги без неожиданностей**
    - Явный статус: “карта привязана / не привязана”.
    - До старта: “что и когда будет списано”.
    - После завершения: экран итогов + чек одним тапом.

### Какие API/модули уже можно использовать под эти улучшения

- `rentals`, `rental-status-history` — основной флоу аренды;
- `payments`, `deposits` — прозрачная финансовая часть;
- `service-requests`, `incidents`, `notifications` — поддержка и коммуникации;
- `geofences`, `fleet-map`, `telemetry-events` — завершение аренды и качество поездки;
- `attachments` — фото при завершении и при инцидентах.

### Минимальный план внедрения (2 недели)

- **Неделя 1:** онбординг, прозрачная цена, новый экран активной аренды с SOS.
- **Неделя 2:** упрощённое завершение аренды + история поездок и чеков.

Ожидаемый эффект: меньше отказов на старте, ниже нагрузка на поддержку, выше доля успешно завершённых аренд.

### KPI, которые стоит отслеживать по UX/UI (еженедельно)

- Conversion to first ride (логин → первая успешная аренда).
- Drop-off по шагам: выбор актива → старт → завершение.
- Доля ошибок завершения аренды с первой попытки.
- Время до успешного старта аренды (TTFR — time to first ride).
- Доля обращений в поддержку на 100 поездок.
- CSAT/NPS после завершённой поездки.

### Что делаем дальше (пошаговый execution-план)

#### Шаг 1 — Discovery и базовые замеры (1–2 дня)

- Зафиксировать baseline по KPI: conversion to first ride, drop-off, TTFR, support/100 поездок.
- Собрать топ-10 обращений клиентов за последние 30 дней и разметить по категориям.
- Утвердить 3 ключевых пользовательских сценария: первая аренда, завершение аренды, проблема во время поездки.

#### Шаг 2 — Быстрые UX/UI победы (3–5 дней)

- Вынести на прод клиентский онбординг в 3 шага.
- Добавить на экран старта аренды прозрачную стоимость (тариф + депозит + возможные списания).
- Добавить SOS-кнопку в активной аренде с пресетами инцидентов.

#### Шаг 3 — Стабилизация критического флоу (5–7 дней)

- Упростить завершение аренды (проверка geofence + фото + итоговая сумма).
- Добавить дружественные тексты ошибок для кейсов: нет сети, слабый GPS, не закрыт замок.
- Снизить количество шагов до целевых значений (старт ≤2, завершение ≤3 + фото).

#### Шаг 4 — Подготовка к масштабированию (параллельно)

- Зафиксировать UI-kit клиентского режима (кнопки, статусы, карточки, алерты).
- Включить A11y-чеклист в Definition of Done (контраст, touch-target, читаемость).
- Настроить еженедельный review KPI с продуктом, саппортом и разработкой.

#### Формат работы команды

- Релизы: 2 раза в неделю (вт/пт), маленькими инкрементами.
- Каждый UX-таск должен содержать: гипотезу, метрику успеха, owner, срок, критерии приёмки.
- После каждого релиза: 24-часовой мониторинг ошибок и обращений поддержки.

#### Критерии “готово” для первой итерации

- Conversion to first ride вырос минимум на 10% от baseline.
- Доля неуспешных завершений аренды снизилась минимум на 20%.
- Обращения в поддержку по “непонятной оплате” снизились минимум на 30%.
