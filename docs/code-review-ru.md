# Code Review (русский)

Дата ревью: 11 мая 2026.

## Что уже есть в проекте

Проект выглядит как зрелый TypeScript monorepo на `pnpm` с хорошей инженерной базой:

- Единый набор quality-gates на уровне root (`typecheck`, `lint`, `test`, `ci`).
- Явная архитектурная декомпозиция на `artifacts/*` (приложения) и `lib/*` (переиспользуемые библиотеки).
- Богатая доменная модель в БД (много таблиц, enum-ы, индексы, связи), реализованная через Drizzle.
- Четко описанные практики эксплуатации в документации (`docs/rollout`, `docs/playbooks`, `docs/release-readiness`).

## Оценка качества кода

### Сильные стороны

1. **Неплохая инженерная дисциплина.**
   В `package.json` есть отдельные скрипты для проверки типов, тестов, линтинга и CI, что упрощает стабильную поставку.

2. **Хорошая типизация на уровне схем.**
   В `lib/db/src/schema/*` таблицы описаны явно, плюс есть Zod-схемы для insert-моделей (`createInsertSchema`) — это снижает шанс рассинхрона между БД и API.

3. **Продуманная многоарендность и RBAC-концепция.**
   Судя по документации и структуре, проект не “CRUD-only”, а полноценная платформа с governance, биллингом и moderation-процессами.

4. **Сильная документация по процессам.**
   Много operational-docs, rollout- и playbook-документов — это хорошо для сопровождения командой.

### Текущие риски/проблемы

1. **Сломан базовый typecheck для библиотек из-за отсутствующего codegen-артефакта.**
   Проверка `pnpm run typecheck:libs` падает на `lib/api-client-react` и `lib/api-zod` (отсутствуют `./generated/*`).

2. **Неочевидный контракт “что должно быть сгенерировано перед сборкой”.**
   Если generated-файлы обязательны, это должно быть встроено в pipeline (`pretypecheck`/`prepare`/`build`), а не оставлено на ручной шаг.

3. **Риск деградации DX для новых разработчиков.**
   Сейчас “клонировал → запустил typecheck” дает immediate fail, что создает лишний барьер входа.

## Что улучшить (приоритетно)

### P0 (сразу)

1. **Добавить автоматический codegen перед typecheck/built-step.**
   Например: `pretypecheck: pnpm --filter @workspace/api-spec run codegen` (или отдельный `bootstrap`-скрипт, который обязателен в CI и локально).

2. **Явно описать минимальный bootstrap в README/CONTRIBUTING.**
   Шаги: install → codegen → typecheck/test.

### P1 (в ближайший спринт)

3. **Добавить guard на актуальность generated-файлов в CI для всех зависимых пакетов.**
   У вас уже есть `codegen:check`; стоит включить его в обязательный CI-пайплайн перед тестами.

4. **Стандартизировать стратегию timestamp-полей в Drizzle-схемах.**
   Сейчас `updatedAt` имеет `defaultNow()`, но обычно еще нужен централизованный механизм обновления при `UPDATE` (через слой репозитория/триггеры/утилиты).

5. **Договориться о едином подходе к decimal/numeric.**
   Для денежных полей (`numeric`) важно зафиксировать правило сериализации (строка/number/Decimal object) в API-контрактах.

### P2 (на улучшение поддерживаемости)

6. **Добавить ADR по multi-tenant boundary и data access policy.**
   Это снизит риск случайных нарушений tenant isolation при новых фичах.

7. **Расширить quality metrics.**
   Помимо unit/integration тестов: mutation testing на критичных доменных сервисах (оплаты, аренда, телеметрия), per-package test coverage budget.

## Итог

**Общее качество: выше среднего / ближе к высокому**, особенно по архитектурному мышлению и процессам. Основная техническая проблема сейчас — не сама бизнес-логика, а надежность developer workflow вокруг codegen-артефактов. После фикса bootstrap/codegen-потока репозиторий станет заметно стабильнее и дружелюбнее для команды.
