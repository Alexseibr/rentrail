Теперь нужно реализовать connected fleet foundation для новой multi-tenant SaaS-платформы аренды bike / ebike / scooter / escooter.

Считать, что уже готовы:
- schema and migrations for core modules
- auth / RBAC / memberships
- CRUD for branches / stations / clients / assets / rentals / blacklist
- payments / deposits / incidents / maintenance / reports foundation
- public pages / inquiries / b2b requests / notifications / feature flags foundation
- audit service
- tenant-safe repositories
- Zod validation
- company / branch guards

## Цель этапа
Заложить clean backend foundation для connected mobility:
1. device registry
2. asset-device binding
3. telemetry ingest
4. telemetry snapshots and events
5. battery foundation
6. geofence foundation
7. command queue foundation
8. map/reporting extensions for telemetry-aware assets

Важно:
- пока не интегрировать конкретного hardware vendor tightly
- строить vendor-agnostic модель
- пока не делать полноценный real-time websocket streaming layer, если это не нужно для foundation
- пока не делать complex route optimization
- архитектура должна быть готова к GPS, battery, smart lock, alarm, geofence, device commands

---

# 1. Общая модель connected fleet

Нужно перейти от просто `asset` к модели:
- asset
- device
- battery
- telemetry
- geofence
- command

При этом:
- asset остается центральной бизнес-сущностью
- device — техническая сущность
- один asset может иметь несколько device bindings
- battery может быть отдельной сущностью для ebike/escooter
- telemetry snapshots/events должны быть tenant-safe
- commands должны идти через queued command model

# 5. Telemetry ingest API

## 5.1. Endpoint
Сделай foundation endpoint:
- POST /telemetry/ingest

Это machine-to-machine endpoint.
Не использовать обычный tenant JWT user auth.

## 5.2. Auth for ingest
Предложи и реализуй простой secure MVP path:
например:
- provider API key
или
- device secret / ingestion token
или
- signed header

Выбери clean minimal design и опиши ее.
Важно:
- не оставляй ingest без auth
- не используй обычный user JWT для device ingest

## 5.3. Input DTO
Payload должен быть vendor-agnostic.
Например:
- provider
- deviceExternalId or deviceId
- recordedAt
- lat/lng
- speed
- heading
- batteryPercent
- batteryVoltage
- lockState
- alarmState
- onlineState
- odometer
- rawPayload optional
- events optional []

## 5.4. Ingest behavior
При приеме:
1. аутентифицируй источник
2. resolve device
3. resolve company
4. optionally resolve active asset binding
5. сохранить telemetry snapshot
6. если есть location -> сохранить location history
7. если есть derived/explicit events -> сохранить telemetry events
8. update device.lastSeenAt
9. optionally update asset lastSeenAt / derived fields if clean for foundation

## 5.5. Idempotency / duplicates
Сделай basic anti-duplicate strategy:
- if same provider + externalId + recordedAt + payload signature repeated, optionally ignore duplicate snapshot
Не overengineer, но хотя бы опиши решение.

# 13. Performance / storage considerations

## 13.1. Important
Telemetry can grow fast.
Сделай clean indexes and storage separation:
- indexes on companyId, assetId, deviceId, recordedAt
- pagination on events/history endpoints
- avoid loading giant payloads by default

## 13.2. Snapshot strategy
Опиши clearly:
- telemetry_snapshots = latest/periodic state table
- location_history = route points
- telemetry_events = meaningful events

If you choose to update one latest snapshot row per asset/device instead of append-only snapshots, explain.
For MVP foundation, append-only + latest query is acceptable, but be explicit.
