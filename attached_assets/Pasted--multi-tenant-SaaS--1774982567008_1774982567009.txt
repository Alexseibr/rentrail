Система должна строиться по модели:

Platform
-> Company
-> Branch
-> Station
-> Assets / Clients / Staff / Rentals / Payments / Incidents / Maintenance / Devices / Batteries

## Основные сущности
- company
- branch
- station
- user
- company membership
- branch membership
- role
- permission
- client
- asset
- rental
- payment
- deposit
- blacklist entry
- incident
- maintenance order
- public inquiry
- b2b request
- device
- battery
- telemetry snapshot/event
- geofence
- command

## Поддерживаемые asset types
- bike
- ebike
- scooter
- escooter

## Строгие принципы
- multi-tenant first
- tenant isolation first
- companyId required for business data
- branchId/stationId where relevant
- asset-first, not car-first
- RBAC + memberships
- auditability
- workflow actions instead of free status patching
- future-ready for telemetry and mobile
- no hardcoded single-company assumptions
- no magic admin bypasses without audit

# 4. IMPORTANT BUSINESS RULES TO PRESERVE THROUGH ALL PHASES

Always preserve these rules:

## Multi-tenancy
- all business data scoped by companyId
- branchId/stationId used where relevant
- never query business entities by id without tenant scope

## Access model
- user may belong to multiple companies
- user may belong to multiple branches
- platform scope separate from tenant scope
- permission-based checks, not only role-name checks

## Assets
- central entity is asset
- supported types: bike / ebike / scooter / escooter
- asset status changes are explicit actions
- asset status history required

## Rentals
- workflow actions required
- not free status patch
- blacklist and asset availability checked before start
- rental status history required

## Blacklist
- branch/company/global scopes
- strongest-action resolution
- not just boolean block flag

## Finance
- deposits have lifecycle
- refund/release/forfeit math must be safe
- audit on all sensitive financial actions

## Connected fleet
- vendor-agnostic
- telemetry ingest separate auth model
- commands queued, not direct inline magic

## UI
- tenant-aware
- branch-aware
- permission-aware
- no mixing platform and tenant scope casually
