Теперь нужно реализовать core CRUD foundation для новой multi-tenant SaaS-платформы аренды bike / ebike / scooter / escooter.

Считать, что уже готовы:
- schema и migrations
- auth
- sessions
- memberships
- RBAC
- company/branch guards
- audit service
- base Express app
- Zod validation
- Drizzle repositories foundation

## Цель
Построить первую рабочую бизнес-часть backend:
- companies
- branches
- stations
- clients
- assets
- rentals
- blacklist

Очень важно:
- все операции должны быть tenant-safe
- company/branch access должен строго проверяться
- history/status transitions должны логироваться
- audit logs должны сохраняться
- никакой single-tenant логики
- никакой car-specific модели

---

# 1. Общие требования к реализации

## 1.1. Архитектура
Для каждого домена используй структуру уровня:
- route/controller
- validator (Zod DTO)
- service
- repository
- mapper/serializer, если нужно

Route handlers должны быть тонкими.
Бизнес-логика должна быть в service layer.
Доступ к БД — через repository layer или аккуратный data-access слой.

## 1.2. Tenant safety
Все list/get/update/create операции должны учитывать:
- company context
- branch scope
- permissions
- membership restrictions

Нельзя доверять companyId/branchId из запроса без проверки.

## 1.3. Soft delete
Где это уместно, используй archivedAt / soft-delete.
Не удаляй бизнес-сущности физически без необходимости.

## 1.4. Audit logging
После create/update/status change/logical delete нужно писать audit record через reusable audit service.

# 6. Asset module

Это критичный модуль. Центральная сущность системы — asset.

## 6.1. CRUD
Реализуй:
- POST /assets
- GET /assets
- GET /assets/:id
- PATCH /assets/:id
- POST /assets/:id/archive
- POST /assets/:id/restore (optional)
- POST /assets/:id/change-status

## 6.2. Asset types
Поддержи:
- bike
- ebike
- scooter
- escooter

## 6.3. List/filter/search
Сделай фильтры:
- assetType
- status
- branchId
- stationId
- isPublic
- search по serialNumber / internalCode / qrCode / brand / model
- pagination
- default sort by createdAt desc

## 6.4. Правила доступа
- asset всегда принадлежит company
- asset закреплен за branch
- station, если указан, должен принадлежать тому же branch/company
- branch-scoped пользователь видит только свои branch assets
- company-level owner/admin/manager могут видеть все assets компании

## 6.5. Status transitions
Нельзя просто PATCH status без правил.
Сделай отдельный service method и endpoint:
- POST /assets/:id/change-status

Допустимые статусы:
- draft
- available
- reserved
- awaiting_pickup
- rented
- overdue
- charging
- maintenance
- blocked
- lost
- stolen
- retired

## 6.6. Asset status history
Каждое изменение статуса должно создавать запись в asset_status_history:
- assetId
- companyId
- fromStatus
- toStatus
- reason
- changedByUserId
- createdAt

## 6.7. Минимальные бизнес-валидации
- serialNumber unique within company
- qrCode unique within company, если задан
- stationId нельзя указать вне branch/company
- retired asset нельзя перевести обратно без явного policy решения; если решишь разрешить — опиши это
- archived asset нельзя использовать в новых rentals

# 7. Rental module

Это второй критичный модуль.

## 7.1. CRUD / workflow
Реализуй:
- POST /rentals
- GET /rentals
- GET /rentals/:id
- PATCH /rentals/:id
- POST /rentals/:id/approve
- POST /rentals/:id/start
- POST /rentals/:id/extend
- POST /rentals/:id/return
- POST /rentals/:id/cancel

Не делай просто generic update status endpoint для rentals.
Нужны явные workflow actions.

## 7.2. Rental statuses
- draft
- pending_approval
- awaiting_payment
- awaiting_pickup
- active
- extended
- overdue
- return_requested
- completed
- canceled
- disputed
- defaulted

## 7.3. Create rental
При создании rental:
- валидируй company/branch/station scope
- client должен принадлежать company
- asset должен принадлежать company и branch
- asset не должен быть archived
- asset не должен быть в incompatible status
- клиент должен пройти blacklist check
- сохрани tariffSnapshot
- сохрани depositAmount
- rentalPlan, если указан, должен принадлежать company

## 7.4. Rental rules
Нужно заложить базовые правила:
- нельзя создать новую активную rental на asset, который уже в active/awaiting_pickup/overdue rental
- нельзя начать rental для blocked/lost/stolen/retired asset
- нельзя start rental для blacklisted client, если actionType = blocked_*
- для warning/manual_approval_only/increased_deposit — вернуть policy flags

## 7.5. Workflow actions
### approve rental
- draft/pending_approval -> awaiting_payment или awaiting_pickup, в зависимости от политики
- логировать status history

### start rental
- только если rental в допустимом статусе
- asset status должен перейти в rented
- создать rental status history
- создать asset status history
- audit log

### extend rental
- обновить plannedEndAt
- опционально сохранить extension reason
- status может остаться active или перейти в extended — выбери clean rule и опиши

### return rental
- зафиксировать actualEndAt
- returnedToStationId
- notes / return summary
- rental status -> completed
- asset status -> available / maintenance / charging в зависимости от payload
- логировать status history
- учесть, что станция возврата должна принадлежать company и быть доступной

### cancel rental
- только в допустимых статусах
- rental status -> canceled
- asset status откатить корректно, если нужно

## 7.6. Rental list filters
Сделай:
- status
- clientId
- assetId
- branchId
- stationId
- date range
- pagination
- default sort by createdAt desc

## 7.7. Rental status history
Каждый переход:
- rentalId
- companyId
- fromStatus
- toStatus
- reason
- changedByUserId
- createdAt

# 8. Blacklist module

## 8.1. CRUD
Реализуй:
- POST /blacklist
- GET /blacklist
- GET /blacklist/:id
- PATCH /blacklist/:id
- POST /blacklist/check

## 8.2. Scope model
Поддержи:
- branch
- company
- global

## 8.3. Action types
- warning
- manual_approval_only
- increased_deposit
- restricted_access
- blocked_branch
- blocked_company
- blocked_global

## 8.4. Access rules
- global entries могут создавать/редактировать только superAdmin/platform-level role
- company entries — owner/admin/manager с нужным permission
- branch entries — branch-capable roles в доступном branch
- list blacklist должен фильтроваться по scope и company context

## 8.5. Check endpoint
POST /blacklist/check должен уметь принимать:
- fullName optional
- phone optional
- email optional
- documentNumber optional
- birthday optional
- clientId optional
- companyId context
- branchId optional

И возвращать:
- exact matches
- matched scopes
- effective decision
- reasons
- recommended action

## 8.6. Effective decision logic
Нужен helper/service, который определяет итог:
- если есть global blocked_global -> hard block
- если есть company blocked_company -> hard block
- если есть branch blocked_branch -> block in branch
- если только warning/manual/increased_deposit -> вернуть restriction flags
- если есть несколько записей — выбрать strongest action

## 8.7. Нормализация
Перед сохранением/check:
- normalize phone
- normalize email
- trim name/document fields
