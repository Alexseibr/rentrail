Теперь нужно реализовать web admin UI foundation для новой multi-tenant SaaS-платформы аренды bike / ebike / scooter / escooter.

Считать, что backend foundation уже существует:
- auth / sessions / RBAC / memberships
- companies / branches / stations
- clients
- assets
- rentals
- blacklist
- payments / deposits
- incidents / maintenance
- reports
- public settings / branding / inquiries / b2b requests / notifications
- telemetry / devices / batteries / geofences / commands foundation

## Цель этапа
Сделать первую рабочую web admin panel, через которую можно:
- логиниться
- выбирать company context
- выбирать branch context
- переходить по разделам
- управлять core сущностями
- видеть dashboard summaries
- работать с inquiries / B2B / notifications
- работать с devices / telemetry reports
- настраивать public page / branding
- подготовить базу для дальнейшей mobile/app/public UI разработки

## Стек
Используй:
- React
- Vite
- TypeScript
- TailwindCSS
- shadcn/ui
- React Router
- TanStack Query (если еще не подключен, подключи)
- Zustand или Context для auth/app context, выбери clean option и объясни
- forms через react-hook-form + zod resolver
- таблицы и фильтры без overengineering

Важно:
- не делать car-specific UI
- UI должен быть asset-first
- tenant-aware
- branch-aware
- role/permission-aware
- modular
- responsive enough, но сейчас приоритет desktop admin experience

# 3. Company and branch context UX

## 3.1. Company switcher
Так как один user может быть в нескольких компаниях, нужен switcher.

Показывать:
- current company
- список доступных companies
- role summary if useful

При переключении:
- сохранять current company in app state
- optionally persist in local storage
- refetch scoped data

## 3.2. Branch switcher / filter
Нужен branch selector:
- all branches, если доступно
- конкретный branch
- only accessible branches
- зависит от memberships

При переключении:
- обновлять active branch context/filter
- не ломать страницы
- branch-restricted users не должны видеть недоступные branches

## 3.3. Context propagation
Все API calls должны использовать active company context и, где нужно, active branch context.

Сделай централизованный API client/interceptor/helper.

# 15. UX rules

## 15.1. Permission-aware pages
Если нет permission:
- либо hide nav item
- либо show access denied page
Оба варианта допустимы, но поведение должно быть consistent.

## 15.2. Loading and empty states
У каждой page/list:
- loading skeleton
- error state
- empty state with useful message/action

## 15.3. Branch scope
Если user branch-restricted:
- скрывай unavailable branches
- не давай выбрать forbidden branch
- filters and forms must respect scope
