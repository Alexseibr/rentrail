- auth/session bootstrap
- company/branch context
- dashboard
- assets list/detail
- rentals list/detail + workflow actions
- clients list/detail
- inquiries list/detail
- incidents list/detail

- reusable mobile UI primitives

## Цель этапа
Добавить в mobile app foundation, которая делает приложение реально пригодным для полевой работы:

1. QR / barcode scanning foundation
2. camera/photo evidence foundation
3. attachment uploads to backend / object storage flow
4. push notifications foundation
5. offline mutation queue foundation
6. background sync hooks foundation

Важно:
- не делать пока сложную offline-first distributed system
- не делать BLE integration сейчас

App по-прежнему staff/operator oriented, а не consumer client app.

Стек:
- Expo / React Native
- TypeScript
- Expo Router or React Navigation (используй то, что уже выбрано)
- Expo Camera / Barcode scanner APIs or equivalent Expo-supported solution
- Expo ImagePicker if needed
- Expo Notifications for push foundation
- Secure local storage / persistence as needed
- TanStack Query + local mutation queue pattern
- clean service abstractions

# 2. QR / barcode scanning foundation

## 2.1. Цель
Сделать reusable scanning flow, который позволяет:
- отсканировать QR транспорта
- отсканировать internal code / barcode / device code
- перейти к соответствующей сущности

## 2.2. Нужен reusable scanner screen/module
Сделай общий scanning module/screen, а не отдельную реализацию в каждом месте.

Поддержи сценарии:
- scan asset QR
- scan asset internal code / barcode
- scan device code
- future-ready for battery QR

## 2.3. Scanner output modes
После сканирования должно быть возможно:
- resolve asset by qrCode/internalCode
- resolve device by externalId/serial/imei if applicable
- fallback to generic scan result callback

## 2.4. Routes / UX
Нужно сделать flow:
- open scanner
- request camera permission
- scan code
- show loading/resolving state
- navigate to resolved entity
- handle not found gracefully

## 2.5. Scanner use cases
Поддержи integration points:
- from assets list → scan asset
- from create rental → scan asset
- from maintenance/incidents → attach scanned asset
- from device screens → scan device

## 2.6. Validation
Сделай simple parser/helper:
- normalize scan text
- identify likely qr/internal/device code
- strip prefixes if needed
- don’t hardcode only one format if avoidable

## 2.7. What NOT to overbuild
Не нужно сейчас:
- multi-code scan sessions
- advanced AR overlays
- batch scanning
- continuous warehouse mode

# 4. Attachment upload foundation

## 4.1. Цель
Сделать clean upload flow from mobile to backend/object storage.

## 4.2. Архитектурный подход
Предпочтительно:
- app requests upload intent / signed upload target from backend
- app uploads file
- app confirms attachment record

Либо:
- app sends multipart to backend if current backend simpler

Выбери clean MVP path и объясни решение.
Важно: не хардкодить upload flow так, чтобы потом невозможно было масштабировать.

## 4.3. Нужен attachment model foundation
Если backend еще не имеет unified attachments model, предложи foundation:
- attachments
или
- entity-specific photos tables with shared abstraction

Но mobile layer должен работать через reusable upload service.

## 4.4. Required flows
Нужно поддержать:
- upload single photo
- attach uploaded photo to incident
- attach uploaded photo to maintenance
- attach uploaded photo to rental return/check flow
- retry failed upload

## 4.5. Error scenarios
Обработай:
- no internet
- upload timeout
- auth expired
- invalid file type
- file too large
- backend rejects attachment

# 6. Offline mutation queue foundation

## 6.1. Цель
При плохом интернете оператор не должен сразу терять действие.
Нужно сделать базовый mutation queue foundation.

## 6.2. Scope
Не нужно делать full offline-first DB sync.
Нужно сделать pragmatic queued actions for selected mutations.

## 6.3. Первые supported queued actions
Выбери небольшой but useful set:
- mark inquiry contacted
- create incident
- create maintenance
- change asset status
- rental return action maybe, if safe enough
- attachment upload retry job

Опиши, какие действия safe for queue in MVP, а какие пока лучше оставлять online-only.

## 6.4. Queue model
Нужен local persisted mutation queue:
- id
- actionType
- payload
- createdAt
- status
- retryCount
- lastError
- companyContext
- branchContext
- dependency info optional

## 6.5. Queue statuses
- queued
- syncing
- failed
- completed
- canceled

## 6.6. Rules
- actions must be idempotency-aware where possible
- network restore should trigger sync attempt
- queue should survive app restart
- user should see pending sync items somewhere simple
- avoid queueing unsafe multi-step workflows without explicit design

## 6.7. UI
Нужен minimal UI/indicator:
- sync pending badge/count
- maybe simple screen in settings/operations:
  - queued actions
  - failed actions
  - retry / discard

# 13. Security and privacy considerations

## 13.1. Camera/media
- handle permissions explicitly
- don’t store sensitive media forever locally after successful upload unless needed
- clean temp files if practical

## 13.2. Push
- unregister token on logout if possible
- tie token to user/device/company context carefully
- avoid leaking sensitive content in push previews unless intended

## 13.3. Offline queue
- persist only necessary payload
- avoid storing secrets in queue
- if queued payload contains sensitive notes, keep local storage choice reasonable and document limitations
