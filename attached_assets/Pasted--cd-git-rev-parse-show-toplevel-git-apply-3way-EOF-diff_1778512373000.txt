+# Code Review (русский)
+
+Дата ревью: 11 мая 2026.
+
+## 1) Что уже есть в проекте
+
+Проект выглядит как зрелый TypeScript monorepo на `pnpm` с хорошей инженерной базой:
+
+- Единый набор quality-gates на уровне root (`typecheck`, `lint`, `test`, `ci`).
+- Явная архитектурная декомпозиция на `artifacts/*` (приложения) и `lib/*` (переиспользуемые библиотеки).
+- Богатая доменная модель в БД (много таблиц, enum-ы, индексы, связи), реализованная через Drizzle.
+- Четко описанные практики эксплуатации в документации (`docs/rollout`, `docs/playbooks`, `docs/release-readiness`).
+
+## 2) Оценка качества кода
+
+### Сильные стороны
+
+1. **Инженерная дисциплина.**
+   В `package.json` есть отдельные скрипты для проверки типов, тестов, линтинга и CI.
+
+2. **Хорошая типизация в data layer.**
+   В `lib/db/src/schema/*` таблицы описаны явно, плюс есть Zod-схемы для insert-моделей (`createInsertSchema`).
+
+3. **Зрелая доменная модель.**
+   По структуре видно, что это полноценная SaaS-платформа (RBAC, billing, moderation, telemetry), а не простой CRUD.
+
+4. **Сильная эксплуатационная документация.**
+   Есть rollout/playbook документы, что важно для поддержки и релизов.
+
+### Текущие риски/проблемы
+
+1. **Сломан базовый typecheck для библиотек без codegen-артефактов.**
+   `pnpm run typecheck:libs` падает на `lib/api-client-react` и `lib/api-zod` (нет `./generated/*`).
+
+2. **Неявный контракт bootstrap/codegen.**
+   Для нового разработчика отсутствует “безошибочный путь” от clone до green-check.
+
+3. **Риск регрессий на стыке API-контрактов и генерации клиентов.**
+   При изменении OpenAPI возможна поломка потребителей, если codegen не встроен в обязательные шаги.
+
+## 3) Проверка дизайна (UI/UX)
+
+Проверил дизайн-структуру на уровне компонентов и навигации (без ручного визуального QA в браузере/эмуляторе):
+
+### Что хорошо
+
+1. **Структурированная навигация и role-based фильтрация.**
+   В `AppLayout` есть группировка меню (main/tools, main/management) и фильтрация доступных пунктов по ролям.
+
+2. **Переиспользуемый компонентный слой.**
+   Есть унифицированные UI-компоненты (например, `Empty`, `PageBreadcrumb`), что обычно уменьшает визуальный дрейф.
+
+3. **Поддержка локализации из коробки.**
+   В layout есть переключение языка `ru/en`.
+
+### Что улучшить по дизайну
+
+1. **Фиксировать дизайн-стандарты как enforceable checks.**
+   Рекомендую добавить visual regression (Playwright snapshots / Chromatic / Loki), иначе дизайн-регрессии ловятся только руками.
+
+2. **Единый UX checklist для ключевых экранов.**
+   Для страниц Fleet/Rentals/Service/Branches: пустые состояния, ошибки загрузки, длинные таблицы, mobile breakpoints.
+
+3. **Accessibility budget.**
+   Ввести обязательный проход `axe` для основных экранов и минимум WCAG AA для контрастов/фокуса/клавиатурной навигации.
+
+## 4) Проверка E2E/интеграционных тестов
+
+### Что фактически проверено
+
+Запущен `pnpm run test:api` (API/E2E набор на базе Vitest). В текущем окружении тесты не смогли стартовать полноценно из-за отсутствия `DATABASE_URL`.
+
+### Текущее состояние
+
+- Упало **18 test suites**.
+- Основная причина: `DATABASE_URL must be set`.
+- Это ограничение окружения, а не обязательно дефект бизнес-логики тестов.
+
+### Можно ли “проверить E2E всех функций”
+
+Коротко: **да, но не в этом окружении без поднятой БД и bootstrap данных**.
+
+Что нужно для полноценного прогона:
+
+1. Поднять PostgreSQL и выставить `DATABASE_URL`.
+2. Прогнать миграции/инициализацию данных (если требуется тестовым setup).
+3. Выполнить:
+   - `pnpm run test:api`
+   - `pnpm run test:integration`
+   - (опционально) web/mobile UI E2E через Playwright/Detox, если добавите такие сценарии.
+

+## 6) Итог
+
+**Общее качество: выше среднего / ближе к высокому.**
+Архитектура и инженерная культура уже хорошие. Главные точки роста — воспроизводимый bootstrap (codegen+db) и автоматизированная проверка UI/E2E, чтобы “проверка всех функций” была действительно стабильной и повторяемой.

+# Локальный workflow разработки (по шагам)
+
+Дата: 11 мая 2026.
+
+## 1) Поднять локальную БД
+
+```bash
+pnpm run dev:db:up
+```
+
+Остановить:
+
+```bash
+pnpm run dev:db:down
+```
+
+Логи Postgres:
+
+```bash
+pnpm run dev:db:logs
+```
+
+## 2) Bootstrap проекта
+
+```bash
+pnpm run dev:bootstrap
+```
+
+Что делает команда:
+
+- codegen API-клиентов,
+- проверка типов библиотек,
+- seed RBAC (только если задан `DATABASE_URL`).
+
+## 3) Полная проверка по порядку
+
+```bash
+pnpm run dev:verify
+```
+
+Порядок:
+
+1. bootstrap,
+2. API-тесты,
+3. integration-тесты.
+
+## 4) Быстрый полный запуск (если установлен docker)
+
+```bash
+pnpm run dev:test
+```
+
+Команда:
+
+- поднимает локальный Postgres,
+- запускает `dev:verify` с дефолтным локальным `DATABASE_URL`, если переменная не задана.
+
+## Если тесты не стартуют
+
+1. Проверьте, что Docker установлен и работает.
+2. Проверьте, что Postgres контейнер запущен.
+3. Проверьте `DATABASE_URL`.
+4. Перезапустите:
+   - `pnpm run dev:db:down`
+   - `pnpm run dev:db:up`
+   - `pnpm run dev:verify`
